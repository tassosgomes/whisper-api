# ADR-003: Allowlist explícita de destinos privados confiáveis (origem e webhook)

## Status

Accepted

## Identidade e escopo

- Caminho: `docs/adr/adr-003.md` (numeração global do repositório)
- Domínios/componentes afetados: Transcrição e Jobs (download de `sourceUrl`); Entrega de Notificações (webhook terminal); configuração de implantação
- Origem histórica: integração com o primeiro consumidor (code-for-coders)
- Substitui: parcialmente a regra "somente HTTPS e somente endereços públicos" de ADR-001 e ADR-002 (apenas para destinos explicitamente listados)

## Data

2026-10-12

## Contexto

A defesa de SSRF do baseline recusa qualquer host que resolva para endereço não global e exige HTTPS, tanto para a `sourceUrl` pré-assinada quanto para o destino do webhook (`app/transcription/paths.py`, `app/transcription/source.py`, `app/jobs/webhooks.py`). O primeiro consumidor e o Whisper estão na mesma rede privada: o MinIO do consumidor (origem da `sourceUrl`) e o receptor de webhook dele têm IP privado, e o MinIO fala HTTP. Com a regra atual a integração é impossível sem expor esses serviços publicamente ou colocar um proxy TLS público na frente deles.

Afrouxar a regra globalmente (por exemplo, aceitar qualquer IP privado ou qualquer `http`) reabriria SSRF contra a rede interna do Whisper (banco, S3 próprio, metadados de nuvem). O usuário decidiu criar uma allowlist explícita, vazia por padrão, mantendo a defesa para todo o resto.

## Decisão

Adotar duas variáveis de ambiente independentes, lidas na inicialização (`Settings.from_env`, e `TRUSTED_PRIVATE_WEBHOOKS` também pelo CLI de webhook):

- `TRUSTED_PRIVATE_SOURCES`: destinos aceitos para `sourceUrl` e para cada redirecionamento do download.
- `TRUSTED_PRIVATE_WEBHOOKS`: destinos aceitos para a URL do webhook (cadastro e entrega).

Uma lista não autoriza a outra. Cada variável é uma lista separada por vírgula de entradas:

```
[http://]host[:porta]      ex.: minio.interno:9000, http://minio.interno:9000, 10.0.0.5:9443
[http://]CIDR              ex.: 10.20.0.0/16, http://10.20.0.0/16, fd00::/8
```

Regras:

1. **Vazia (padrão) = comportamento anterior.** Somente HTTPS e somente endereços globais.
2. **Critério de aceitação.** Um destino privado só é aceito se (a) o hostname e a porta da URL casarem com uma entrada de host, ou (b) todos os IPs resolvidos caírem em algum CIDR listado. Entrada de host sem porta vale para a porta padrão do seu esquema (443 ou 80); entrada CIDR vale para qualquer porta. Não há curinga de nome.
3. **HTTP só com marcação.** O prefixo `http://` torna a entrada válida para URLs `http`; entradas sem prefixo valem somente para `https`. As entradas são específicas por esquema: `http://h:9000` não autoriza `https://h:9000`, e uma entrada sem prefixo nunca autoriza `http`. Sem entrada que o autorize, `http` continua recusado, inclusive para hosts públicos.
4. **Nunca permitidos**, mesmo se listados (por host ou por CIDR, como `0.0.0.0/0`): loopback, link-local (169.254.0.0/16, que inclui metadados de nuvem, e fe80::/10), multicast e endereço não especificado. Endereços IPv6 mapeados em IPv4 são avaliados pelo IPv4 embutido. Basta uma resposta DNS proibida para recusar o destino.
5. **Redirecionamentos** continuam validados a cada salto com as mesmas regras e a mesma lista (origem). Um redirecionamento de host listado para destino privado não listado, para loopback/link-local ou para esquema não autorizado é recusado antes de qualquer conexão. O webhook continua sem seguir redirecionamentos (3xx é falha, ADR-002).
6. **Conexão pinada.** A conexão continua fixada ao endereço aprovado na resolução (anti DNS rebinding). Para `http` aprovado usa-se conexão não-TLS pinada; para `https` mantém-se a verificação de certificado e de hostname.
7. **Implementação única.** Uma função de política (`resolve_destination_addresses`) e um parser (`TrustedDestinations`) em `app/transcription/paths.py` são reutilizados pela origem e pelo webhook, cada um com a sua lista; as conexões pinadas HTTP/HTTPS ficam em `app/transcription/pinned.py`.
8. **Falha fechada.** Entrada malformada na variável impede a inicialização (`ValueError`), em vez de ser ignorada.

## Alternativas Consideradas

### Aceitar qualquer IP privado quando uma flag global estiver ligada

- **Prós:** Configuração trivial.
- **Contras:** Expõe toda a rede interna (banco, S3 do Whisper, serviços vizinhos) a SSRF via `sourceUrl` ou redirecionamento.
- **Por que rejeitada:** Não limita o raio de ação ao destino necessário.

### Proxy TLS público na frente do MinIO e do receptor do consumidor

- **Prós:** Não exige alterar o Whisper.
- **Contras:** Expõe serviços internos à internet e adiciona infraestrutura apenas para contornar a validação; o tráfego já é interno.
- **Por que rejeitada:** Aumenta a superfície de ataque do consumidor.

### Lista única para origem e webhook

- **Prós:** Uma variável só.
- **Contras:** Autorizar o MinIO como destino de webhook (ou o receptor como origem) amplia permissões sem necessidade.
- **Por que rejeitada:** Privilégio mínimo; o usuário pediu variáveis separadas.

## Consequências

### Positivas

- A integração privada funciona sem afrouxar a defesa para o restante dos destinos.
- Comportamento padrão inalterado; a exceção é explícita, versionável em configuração e auditável.
- Lógica de política e conexão pinada centralizada em vez de duplicada.

### Negativas

- Um operador pode listar um CIDR amplo (ex.: `10.0.0.0/8`) e liberar mais do que o necessário; a documentação recomenda host:porta ou CIDR mínimo.
- `http` em rede privada não tem confidencialidade nem integridade em trânsito: a `sourceUrl` pré-assinada (credencial temporária) trafega em claro nesse trecho. O corpo do webhook continua assinado (ADR-002), mas legível.
- Mudar a lista exige reiniciar API e worker.

### Riscos

- Host listado cujo DNS passe a apontar para outro serviço privado: mitigado parcialmente pelo bloqueio permanente de loopback/link-local/multicast e pela porta explícita; prefira IP/CIDR fixo para serviços críticos.
- Entrada `http://` com CIDR amplo autoriza HTTP para qualquer porta nesse intervalo; usar o menor intervalo possível.
