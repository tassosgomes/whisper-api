# ADR-005: Cliente desktop Windows em .NET e WPF, no repositório do Whisper

## Status

2026-10-21

## Contexto

CAP-004 cria um aplicativo para Windows 11 que grava o microfone e o áudio do sistema, guarda áudio e transcrição no PC, envia o áudio por URL pré-assinada ao S3 do Whisper e acompanha o job por consulta. Os requisitos que mais pesam na escolha da plataforma são: captura confiável do áudio que o PC reproduz sem driver de terceiros (RF-09), persistência contínua da gravação para sobreviver a fechamento, queda e disco cheio (RN-G01), troca de dispositivo no meio da gravação (RF-02), funcionamento em segundo plano por reuniões de até duas horas, guarda protegida da API Key (RN-G07) e notificação do Windows (RF-06). O PRD limita o app a Windows 11 e deixa outros sistemas operacionais fora do escopo.

O Domain Map e o baseline cobriam só o serviço. Este é o primeiro cliente próprio do Whisper e não tinha stack, local de código nem guardrails.

## Decisão

- Plataforma: .NET com WPF, somente Windows 11. A captura usa WASAPI (microfone e loopback do sistema), sem driver nem cabo virtual.
- Código no repositório do Whisper, em `clients/`, ao lado do PRD e do contrato, para que mudança de contrato e de cliente trafeguem no mesmo PR. Um repositório próprio exige nova ADR.
- O cliente é consumidor externo da API pública, como qualquer outro. Não importa código do serviço Python nem acessa seu banco ou fila. O cliente de API é gerado a partir de `api-contract.yaml`.
- Os guardrails do cliente ficam no baseline arquitetural, na seção "Clientes do Whisper".
- O rótulo exato do framework de UI (por exemplo, tema Fluent) e as bibliotecas de áudio e de instalação são escolhas da TechSpec.

## Alternativas Consideradas

### Electron com TypeScript

- **Descrição:** app em Electron, com captura via `getDisplayMedia` em modo loopback e gravação por `MediaRecorder`.
- **Prós:** domínio de TypeScript, interface mais livre, caminho para macOS e cliente gerado com `openapi-typescript`.
- **Contras:** a captura do sistema depende de comportamento do Chromium e do fluxo de captura de tela; o consumo de memória e o tamanho do instalador são maiores para um app que fica em segundo plano; exige endurecer o processo e acompanhar as correções de segurança do Chromium.
- **Por que rejeitada:** o núcleo do produto é a captura confiável e leve, o escopo é só Windows 11 e macOS é non-goal.

### Tauri (Rust e webview)

- **Descrição:** shell nativo leve com interface web.
- **Prós:** pequeno e leve.
- **Contras:** captura de áudio do sistema e ecossistema de áudio menos maduros para este caso, e outro runtime para manter.
- **Por que rejeitada:** não reduz o risco da captura.

### Repositório separado para o cliente

- **Descrição:** cliente com ciclo de release próprio.
- **Prós:** independência de release.
- **Contras:** o contrato e o PRD precisam ser copiados ou publicados; mudança de API e de app deixam de ser atômicas.
- **Por que rejeitada:** não há equipe nem cadência independentes que a justifiquem hoje.

## Consequências

### Positivas

- Captura de áudio e eventos de dispositivo pelas APIs do Windows, com pouco consumo em segundo plano.
- Credential Manager ou DPAPI para a API Key, e notificação, bandeja e atalho global nativos.
- Contrato, PRD, API e cliente evoluem juntos.

### Negativas

- Só Windows. Levar o app a macOS exige reescrever a interface e a captura.
- O repositório passa a ter uma segunda stack (.NET ao lado de Python), com build, testes e CI próprios.
- WPF sem tema Fluent parece datado; a TechSpec deve decidir o tema.

### Riscos

- O tipo de dispositivo de áudio e o modo exclusivo variam entre PCs; mitigação no PRD (indicador de nível, mensagens claras) e prova de captura na TechSpec.
- Mistura de duas fontes de áudio pode dessincronizar; a TechSpec deve definir como alinhar os relógios.

## Notas de Implementação

Local sugerido: `clients/windows-recorder/`. Versão exata do .NET, bibliotecas de áudio e de instalação e o pipeline de CI ficam para a TechSpec.
