# ADR-004: Sessão operacional distinta da API Key

## Status

Accepted (2026-10-21)

## Identidade e escopo

- Caminho: `docs/adr/adr-004.md`
- Domínios/componentes afetados: Acesso e Contas; superfície HTTP do operador no monólito
- Origem histórica: CAP-002, console operacional, 2026-10-14
- Substitui: Nenhuma

## Data

2026-10-14

## Contexto

O operador precisa administrar contas, API Keys e destinos, e ler a fila de todas as contas. A API pública já autentica máquinas com `X-API-Key`. A credencial do operador é compartilhada, não identifica uma pessoa e não pode criar nem consultar jobs na API pública. A API Key do cliente não pode abrir a administração.

O monólito modular continua sendo a fronteira de deploy. A tela e a API pública compartilham o host. Tratar a credencial operacional como mais uma API Key misturaria privilégio de máquina e privilégio de operação no mesmo verificador.

## Decisão

A credencial operacional entra por formulário no mesmo host. O serviço compara o segredo com a configuração do processo, em tempo constante, e abre uma sessão. O cookie `operator_session` é HttpOnly e carrega só o identificador da sessão, não o segredo e não uma API Key.

`X-API-Key` continua sendo o único scheme da API pública de transcrição. Cookie de operador nessa API não autentica. API Key nas rotas do operador não autentica. O segredo operacional não é gravado na tabela de credenciais nem cifrado com a chave do material de webhook.

## Alternativas Consideradas

### Alternativa 1: Segredo operacional no cabeçalho, no mesmo estilo da API Key

- **Descrição:** o operador enviaria o segredo compartilhado em um header próprio, recusado na API pública.
- **Prós:** sem estado de sessão no servidor.
- **Contras:** o navegador passaria a guardar e reenviar um segredo de longo prazo; o vazamento do header se confunde com vazamento de API Key.
- **Por que rejeitada:** a credencial é de pessoas operando uma tela, não de uma máquina chamando a API.

### Alternativa 2: Reusar `X-API-Key` com uma conta interna de operador

- **Descrição:** uma credencial comum, marcada como administrativa, abriria o console e a API.
- **Prós:** um único verificador.
- **Contras:** a mesma chave criaria jobs e veria a fila de todas as contas. A revogação de máquina e a de operação deixam de ser independentes.
- **Por que rejeitada:** contradiz a separação já aceita entre credencial de máquina e privilégio operacional.

## Consequências

### Positivas

- A tela pode ser servida no mesmo host sem novo serviço.
- Perder a sessão não revela API Key nem material de webhook.

### Negativas

- O processo passa a ter estado de sessão, ou um identificador opaco equivalente, além das tabelas já duráveis de job e credencial.
- Quem possui o segredo compartilhado continua vendo todas as contas. A trilha não nomeia uma pessoa.

### Riscos

- Comparar o segredo operacional dentro de `CredentialStore.authenticate` aceitaria a credencial de operação como API Key. A mitigação é um verificador separado, que não consulta a tabela de credenciais.
- Logar o corpo de `POST /operator-sessions` gravaria o segredo. A mitigação é não registrar esse corpo nem o valor comparado.

## Notas de Implementação

A comparação usa o segredo configurado no ambiente do processo. Rotacionar esse segredo invalida o acesso até o novo valor ser distribuído a quem opera. Sessões já abertas deixam de valer quando o segredo muda, porque não são API Keys reutilizáveis.

Ações administrativas registram momento, o fato de terem sido feitas pela credencial operacional, a conta, o objeto e o motivo quando a ação o exige. O registro não contém segredo, mídia, transcrição nem URL de origem.
